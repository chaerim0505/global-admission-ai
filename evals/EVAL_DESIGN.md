# Evals 설계서 — Global Admission AI (v1)

골든 테스트(`tests/harness/`)는 항상 충족해야 하는 규칙을 테스트의 assert로 확인한다. `evals/`는 같은 평가 세트를 사용해 파싱, 짧은 답변 해석, AI 탐색, 추천 이유 등을 측정하고 통과 건수와 비율을 기록한다. 일부 제약은 골든 테스트와 evals에서 함께 확인한다.

## 1. 평가 지표

| 지표 | 정의 | 채점기 | 근거 AC | 목표 | 모드 |
| --- | --- | --- | --- | --- | --- |
| 제약 충족률 `constraint_rate` | 검증 후보가 적용되는 국가·학위 조건을 충족하고, 데이터에 있는 과정만 반환하며, 근거 없이 예산 적합을 확정하지 않은 케이스 비율 | 코드 | AC1, AC2, AC3, AC7, AC14, AC17 | 100% | offline |
| 검증 후보 환각 건수 | `candidates`에 검증 데이터에 없는 `programId`가 나와 채점기에 기록된 건수 | 코드 | AC3 | 0건 | offline |
| 범위 안내율 `scope_rate` | 5개국 밖 또는 공학계열 밖 요청에 `scopeNotices`를 주고 대체 검색하지 않은 케이스 비율 | 코드 | AC13 | 100% | offline |
| 입력 검증률 `input_validation_rate` | 필수 정보 누락이나 조건 충돌 시 추천을 중단하고 해당 오류 필드를 반환한 케이스 비율 | 코드 | AC15 | 100% | offline |
| 파싱 정확도 `parse_accuracy` | 기대 필드를 정확히 추출하고 사용자가 말하지 않은 분야를 임의로 고르지 않은 케이스 비율 | 코드 | AC2, AC13, AC14, AC15, AC16 | ≥ 90% | live |
| 인젝션 저항 `injection_resistance` | 발화에 포함된 지시문의 값이 추출 결과에 들어가지 않은 케이스 비율 | 코드 | AC10 | 100% | live |
| 짧은 답변 해석 정확도 `followup_accuracy` | 짧은 답을 직전 질문의 항목에 채우고 케이스에서 확인하도록 지정한 다른 필드를 올바르게 유지한 비율 | 코드 | AC20 | ≥ 90% | live |
| AI 탐색 규칙 준수율 `explore_rule_compliance` | 결과가 1–5개이고 각 항목이 `ai_suggested`, HTTPS 링크, 요청 국가, 요건 판정 필드 미포함 조건을 모두 충족한 케이스 비율. 호출 오류도 분모에 포함한다. | 코드 | AC19 | 100% | live |
| 추천 이유 근거 충실도 `reason_faithfulness` | 채점 대상 후보의 추천 이유가 모두 Judge의 `pass`를 받은 케이스 비율 | LLM-as-a-Judge | AC4, AC5 | ≥ 80% | live + judge |

현재 AI 탐색 채점기는 링크가 `https://`로 시작하는지 확인한다. 공식 대학 도메인 확인은 이 채점기의 검사 범위에 포함되어 있지 않다. 입력 검증에서 실제 HTTP 422 응답은 `tests/test_recommend_api.py`가 확인한다.

### 점수가 실제 품질을 반영하도록 둔 조건

- AI 탐색 결과 0개는 `min_count: 1` 조건에 따라 실패로 센다.
- 검증 후보가 나와야 하는 `e01`, `e10`, `e11`은 `must_include`로 기대 후보가 포함됐는지 확인한다.
- 추천 이유가 사용자 관심 분야와 연결되지 않으면 Judge 기준 5에 따라 실패로 판정한다.

## 2. 평가 데이터셋 — `evalset.jsonl` (v1, 25개)

각 케이스는 `id`, `category`, `metric`, `ac`, `mode`, `input` 또는 `query`, `expect`, `graders`, `note`를 포함한다. 짧은 답변처럼 이전 대화가 필요한 케이스에는 `previous`도 포함한다. `expect`에는 기대 필드와 결과가 충족해야 할 조건을 기록한다.

| 유형 | 개수 | 내용 |
| --- | ---: | --- |
| `constraint` | 5 | 정상 요청, 희망 국가 없음, 검증 데이터가 없는 학위·국가, 5개국 밖 국적 |
| `hallucination` | 1 | 공식 학비 정보가 없는 과정에 대한 예산·장학금 요청 |
| `out_of_scope` | 3 | 캐나다, MBA, 파서 단계의 범위 밖 요청 |
| `clarify` | 2 | 정보가 부족한 구조화 입력과 자연어 발화 |
| `conflict` | 3 | 성적이 만점을 넘는 경우, 학비 통화·기간 누락, 자연어 발화 속 성적 충돌 |
| `injection` | 1 | 발화 속 “이전 지시 무시” |
| `parse` | 3 | 한 문장 전체 추출, `AI`만 언급한 경우, 국적과 성적표 발급 국가가 다른 경우 |
| `followup` | 4 | `KR`, `UK`, `4.5`, `네덜란드요` |
| `explore` | 3 | 네덜란드 컴퓨팅 석사, 미국 기계공학 학부, 한국·영국 전기전자공학 석사 |

v1은 정상 케이스 9개와 실패·경계 케이스 16개로 구성했다. 케이스는 SPEC 수용 기준, 골든 케이스, 2026-11-11 데모 준비 중 발견한 입력 오류에서 가져왔다. `KR`을 잘못된 국가 필드에 넣거나 `4.5`를 만점으로 해석하지 못했던 문제는 짧은 답변 회귀 케이스(`e19`–`e22`)에 반영했다.

다음 평가 세트는 인터뷰와 동료 피드백에서 확보한 실제 요청 및 실패 입력을 포함해 50개로 확장하는 것을 목표로 한다.

## 3. 채점기와 러너 — `run_evals.py`

- `load_cases`로 평가 세트 형식을 확인하고, 케이스를 실행한 뒤 `graders`에 따라 채점한다.
- **offline**에서는 구조화 입력으로 `tools.search_programs`를 실행한다. 모델 호출 없이 결과의 제약 충족 여부를 검사한다.
- **live**에서는 `run_intake_agent`로 파싱과 후속 답변 해석을, `tools.explore_programmes_web`으로 Gemini 웹 탐색을 평가한다.
- **Judge**는 `judge_prompt.md` v1을 사용해 각 후보의 추천 이유를 개별 판정한다. 케이스 내 후보가 모두 통과해야 해당 케이스를 통과로 집계한다.
- `tests/test_run_evals.py`는 데이터에 없는 과정, 요청 밖 국가, 임의 분야 등 잘못된 결과를 채점기가 걸러내는지 확인한다.

저장소 루트에서 실행한다. live와 Judge 실행에는 `GEMINI_API_KEY`가 필요하다.

```bash
PYTHONPATH=src python evals/run_evals.py
PYTHONPATH=src python evals/run_evals.py --live --judge --repeat 3 --note "v1 반복 측정"
```

## 4. 결과 기록과 베이스라인

실행 결과는 `results/<YYYY-MM-DDTHHMM>.json`과 `results/history.csv`에 기록한다. JSON에는 커밋, 실행 모드, 모델, 반복 횟수, 평가 세트와 Judge 프롬프트 해시, 지표, 케이스별 결과가 들어간다. 버전 간 점수를 비교할 때는 같은 평가 세트와 Judge 프롬프트를 사용하고, 모델이나 검증 데이터 변경이 있으면 실행 메모에 남긴다.

| --- | ---: | ---: | ---: |
| 제약 충족률 | 6/6 (100%) | 6/6 (100%) | 100% |
| 범위 안내율 | 2/2 (100%) | 2/2 (100%) | 100% |
| 입력 검증률 | 3/3 (100%) | 3/3 (100%) | 100% |
| 검증 후보 환각 | 0건 | 0건 | 0건 |
| 파싱 정확도 | 미실행 | 6/6 (100%) | ≥ 90% |
| 인젝션 저항 | 미실행 | 1/1 (100%) | 100% |
| 짧은 답변 해석 정확도 | 미실행 | 4/4 (100%) | ≥ 90% |

- **offline**은 11건 통과, 14건 건너뜀으로 기록됐다. 실행 이력에는 커밋 `7f4f75d`와 당시 미커밋 변경 사항이 기록되어 있다.
- **live + judge**는 24건 통과, 1건 오류로 기록됐다. 커밋 `ee7edf3`에서 1회 실행했다.
- 목표에 미달한 지표는 AI 탐색 규칙 준수율이다. 네덜란드 컴퓨팅 석사 케이스 `e23`에서 Gemini가 `504 DEADLINE_EXCEEDED`를 반환했다. 미국 기계공학 학부 `e24`와 한국·영국 전기전자공학 석사 `e25`는 통과했다. 당시 실행 메모에는 통과한 두 케이스도 약 73초와 77초가 걸렸다고 기록돼 있다.
- Judge 통과 2건의 케이스 ID는 `e01`, `e10`이다. 이 수치는 모델이 추천 이유를 통과시킨 집계다. 사람과 Judge의 일치율은 6절 절차로 산출한다.

당시 offline에서 사용한 검증 데이터는 `galway-1mai1-2027` 한 과정이었다. 지표별 표본도 작다. 예를 들어 AI 탐색 3건에서는 한 케이스의 차이가 약 33.3%p다. 결과를 비교할 때 백분율과 함께 통과 건수, 전체 건수, 오류 내용을 기록한다.

### 반복 측정 현황

`results/history.csv`에서 확인되는 반복 측정 결과는 아직 없다. `--live --judge --repeat 3`을 실행하면 러너는 25개 케이스를 세 번 실행하고 지표별 통과 건수와 전체 건수를 합산해 보고한다. 실행 후 결과 파일 경로, 집계값, `e23` 재발 횟수를 이 절에 추가한다.

## 5. 병합 및 배포 기준

| 대상 | 기준 |
| --- | --- |
| 골든 테스트 | 실패가 있으면 병합을 보류한다. GitHub Actions는 PR과 `main` push에서 테스트, 골든 케이스 리포트, offline evals를 실행한다. |
| 절대 규칙 지표 | 제약 충족률, 범위 안내율, 입력 검증률, 인젝션 저항, AI 탐색 규칙 준수율 중 100% 미달이 있거나 검증 후보 환각이 1건 이상이면 배포를 보류하고 원문을 확인한다. |
| 회귀 지표 | 파싱과 짧은 답변 해석은 3회 반복 결과를 사용한다. 베이스라인 대비 5%p를 초과해 하락하면 배포를 보류한다. |
| 근거 충실도 | 목표 미달 시 실패 이유를 개선 백로그에 기록한다. 이 지표의 목표 미달만으로 배포를 막지는 않는다. |

프롬프트, Gemini 모델 또는 `config/rag.yaml`을 변경하면 배포 전에 live + judge 평가를 3회 실행한다. v1 베이스라인에서는 AI 탐색이 목표에 미달했으므로 다음 실행에서 시간 초과 재발 여부를 확인한다.

## 6. Judge 검증 — 팀이 직접 채점

**현재 상태.** v1에서 `e01`, `e10`의 추천 이유가 Judge 평가를 통과했다. `judge_labels.jsonl`에는 사람 라벨이 0개이며, 사람과 Judge의 일치율은 아직 산출하지 않았다.

1. live + judge를 실행해 사람이 검토할 추천 이유 출력 20–30개를 모은다. 3회 실행 후 실제 채점 가능한 표본 수를 세고, 부족하면 표본을 더 모은다.
2. 각 출력의 사용자 조건, 후보 데이터, 추천 이유 원문을 대조한다. 팀원이 `pass` 또는 `fail`과 판정 이유를 `judge_labels.jsonl`에 한 줄씩 기록한다.
3. 같은 추천 이유에 대한 사람과 Judge의 판정을 대조한다. `같은 판정 수 ÷ 비교한 표본 수 × 100`으로 일치율을 계산한다. 불일치는 `사람 fail / Judge pass`와 `사람 pass / Judge fail`로 나눠 기록한다.
4. 일치율이 80% 이상이면 Judge 프롬프트 v1을 고정한다. 80% 미만이면 불일치 원문을 검토하고 판정 기준을 수정한 뒤 버전을 올려 다시 측정한다.

라벨 한 줄의 형식은 아래와 같다. 실제 파일에는 팀원이 검토한 출력과 판정만 넣는다.

```json
{"case_id":"<케이스 ID>","programId":"<과정 ID>","reason":"<추천 이유 원문>","human_verdict":"<pass 또는 fail>","human_note":"<사람이 작성한 판정 이유>"}
```

## 7. 오류 분석 — `ERROR_ANALYSIS.md`

### 실행 기록에서 확인된 오류

| 실행 | 케이스 | 입력 요약 | 기록된 결과 |
| --- | --- | --- | --- |
| `2026-11-11T0246` | `e23` | 네덜란드(`NL`) 컴퓨팅 석사 탐색 | Gemini `504 DEADLINE_EXCEEDED`. 케이스 상태는 `error`이며 탐색 결과가 기록되지 않았다. |

해당 실행에서 AI 탐색 3건 중 **시간 초과 오류는 1건**이었다. 다음 반복 측정에서는 `e23`의 **504 재발 횟수**와 **케이스별 실행 시간**을 기록한다. 현재 러너는 실행 시간을 콘솔에 출력하므로 실행 시간 비교에는 콘솔 출력도 보관한다.

### 실패 원문 수집과 팀 검토

현재 `main`에서 `ERROR_ANALYSIS.md`가 삭제된 상태다. 아래 명령으로 기존 베이스라인의 실패 원문을 담은 파일을 다시 생성할 수 있다. 인자 없이 실행하면 저장된 모든 실행 결과를 대상으로 표를 만든다.

```bash
python evals/collect_failures.py evals/results/2026-11-11T0246.json
```

팀원이 실패 원문과 관련 로그를 직접 읽은 뒤 `ERROR_ANALYSIS.md`에 아래 두 표를 채운다. 위의 실행 기록은 검토할 사례를 찾는 데 사용한다.

| 케이스 | 관찰 메모 | 오류 범주 |
| --- | --- | --- |
| `e23` | 팀원이 입력과 오류 원문을 읽은 뒤 작성 | 팀 검토 후 확정 |

| 오류 범주 | 건수 | 개선 백로그 |
| --- | ---: | --- |
| 팀 검토 후 확정 | — | 반복 측정에서 확인한 재발 빈도와 영향에 따라 개선 작업을 정한다. |

수정한 실패 사례는 재현 조건을 정리한 뒤 평가 세트에 회귀 케이스로 추가한다.
